How to use this page

⏱ 2 min

Read this bit once, then never again.

Every grey box below is a command. Click Copy, paste it into your terminal, press Enter. Nothing on this page runs by itself — you are always in control.

💡 Pick your system first ☝

Use the Windows / Mac & Linux switch at the top of this page. Some commands are different on each system, and the page will show you only the ones that work on your machine. Get this wrong and half the commands will fail.

⚠ Windows users: use PowerShell

Not Git Bash, not the old cmd window. PowerShell handles interactive containers correctly and everything on this page is tested for it.

Grey boxes with a inside container tag are typed inside a running container, not in your normal terminal. You will always be told when you go in and how to get out.

Check that Docker is alive

⏱ 3 min

Two commands. If both work, you are ready for the whole class.

✓

Is the Docker command installed?

Asks Docker to print its version number. This only proves the client (the docker command) exists.

docker --version
What you should see
Docker version 27.3.1, build ce12230
✓

Is the Docker engine running?

Lists running containers. It should print a table with headers only and no rows — that empty table is the proof that your docker command reached the Docker engine running in the background.

docker ps
What you should see
CONTAINER ID   IMAGE   COMMAND   CREATED   STATUS   PORTS   NAMES
✅ Both worked?

Skip the next section entirely and jump straight to Step 2.

⚠ Something failed?

Open the next section — it has the fix for every common error. If you are stuck for more than 3 minutes, raise your hand and switch to Play with Docker (a free Docker terminal in your browser, needs a free Docker Hub account) so you can still follow along.

3

The old way — run the app on your own laptopoptional

⏱ 10 min

Before Docker, this was the routine. Feel the pain first, then the fix makes sense.

Our app is a small FastAPI web service. To run it the traditional way you need the right Python version, a virtual environment, and the right packages — on every single machine that will ever run it. Let's do it once.

✓

Create a virtual environment

A private folder (.venv) holding a copy of Python and this project's packages, so they never clash with your other projects.

py -m venv .venv
python3 -m venv .venv
✓

Allow the activation script to run (this window only)

Windows blocks scripts by default. This unblocks it for the current PowerShell window only — it changes nothing permanently.

Set-ExecutionPolicy -Scope Process -ExecutionPolicy Bypass -Force

Not needed on Mac or Linux — skip to the next command.

✓

Activate the virtual environment

Switches your terminal to use the project's private Python. You will see (.venv) appear at the start of your prompt — that is how you know it worked.

.\.venv\Scripts\Activate.ps1
source .venv/bin/activate
What you should see
(.venv) PS C:\...\project>
✓

Install every dependency in one go

Reads requirements.txt and installs exactly those packages at exactly those versions.

python -m pip install -r requirements.txt
pip install -r requirements.txt
What you should see
Successfully installed fastapi-0.141.1 uvicorn-0.53.0 ...
✓

Start the app

Runs the web server. Now open http://localhost:8000 in your browser.

python -m uvicorn app:app --port 8000
uvicorn app:app --port 8000
What you should see
Uvicorn running on http://127.0.0.1:8000 (Press CTRL+C to quit)
⏹ Stop it before moving on

Press Ctrl + C in the terminal to stop the server. Then type deactivate and press Enter to leave the virtual environment.

💡 So what was the problem?

That worked… on your machine. Hand this folder to someone with Python 3.9, or a locked-down work laptop, or a Linux server with no compiler, and the install breaks. The app needs a specific Python, specific packages, specific system libraries — and requirements.txt only describes one of those three.

Docker packages all three. That is the entire idea. Let's go.

4

Your first container

⏱ 5 min

The smallest possible container, so you can watch the whole workflow happen.

✓

Run the hello-world container

Docker looks for the hello-world image on your machine, does not find it, downloads it from Docker Hub, starts a container from it, prints a message, and the container exits.

docker run hello-world
What you should see
Hello from Docker!
This message shows that your installation appears to be working correctly.
💡 What actually happened, in order
  1. Looked for the image locally → not found
  2. Pulled it from Docker Hub (the app store for images)
  3. Created a container from that image
  4. Ran it → it printed the message
  5. Exited — the container stopped, but it still exists

That is the whole Docker workflow you will repeat all day: pull → run → stop → remove.

✓

Run it a second time

Notice how much faster it is. The image is already on your disk, so there is nothing to download. This is the first hint of why Docker feels fast.

docker run hello-world
5

Images: download and inspect them

⏱ 7 min

An image is a read-only template. A container is a running copy of it.

✓

Download the Python image we will use later

pull downloads an image without running it. 3.11-slim is the tag: Python 3.11, slim variant (~150 MB instead of ~1 GB).

docker pull python:3.11-slim
What you should see
3.11-slim: Pulling from library/python
Status: Downloaded newer image for python:3.11-slim
✓

Download a tiny web server image

nginx is a real production web server. The alpine tag is a stripped-down build, about 20 MB.

docker pull nginx:alpine
✓

List the images you now own

Columns: REPOSITORY (name), TAG (version), IMAGE ID (unique id), CREATED, SIZE.

docker images
What you should see
REPOSITORY   TAG         IMAGE ID       CREATED       SIZE
python       3.11-slim   1a2b3c4d5e6f   2 weeks ago   150MB
nginx        alpine      9f8e7d6c5b4a   3 weeks ago   48MB
hello-world  latest      d2c94e258dcb   8 months ago  13.3kB
💡 Tags matter more than people think
  • python:3.11 — full image, every tool included (~1 GB)
  • python:3.11-slim — minimal but fully compatible ← use this
  • python:3.11-alpine — smallest, but some packages refuse to install
  • python:latest — whatever is newest today. Never use in production: your build changes under your feet.
6

Run a real server & map a port

⏱ 10 min

Port mapping is the one thing everybody gets wrong on day one. We will make it obvious.

✓

Start nginx in the background

-d detached, runs in the background · -p 8080:80 connects port 8080 on your laptop to port 80 inside the container · --name gives it a name you can remember instead of a random id.

docker run -d -p 8080:80 --name my-nginx nginx:alpine
What you should see
e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855
✅ Now open it in your browser

http://localhost:8080 — you should see “Welcome to nginx!”

You did not install nginx. You have no config files. It took two seconds. That is the point.

💡 The -p rule, once and for all

-p <your laptop>:<inside the container>

A container is a sealed box. Nothing gets in unless you open a door. -p 8080:80 says “knocks on my port 8080 get delivered to port 80 inside”. Swap the numbers around and nothing works — that is the #1 day-one mistake.

✓

See it running

Lists running containers. Look at the PORTS column — it shows your mapping.

docker ps
✓

Read the server's logs

Everything the app printed. Refresh the browser page a few times first, then run this again — you will see your own requests appear. This is the first thing you check when something breaks.

docker logs my-nginx
✓

Follow the logs live (optional)

-f streams new log lines as they happen. Refresh the browser and watch. Press Ctrl + C to stop watching — this does not stop the container.

docker logs -f my-nginx
7

Container lifecycle: stop, start, remove

⏱ 8 min

Stopped is not deleted. That difference confuses everybody once.

✓

Stop the container

Politely asks the process inside to shut down. The container stops but still exists on disk.

docker stop my-nginx
✓

Prove it is gone from the running list

Empty table. The browser tab at :8080 will also stop working now.

docker ps
✓

Now list ALL containers, including stopped ones

-a = all. There is your stopped nginx, status Exited. It still takes up disk space — stopped containers are not deleted containers.

docker ps -a
✓

Start it again

Same container, same settings, back to life. No re-download, no re-typing of the port mapping.

docker start my-nginx

ⓘ Refresh http://localhost:8080 — it is back.

✓

Delete it for good

-f stops it first if it is running, then removes it. Without -f you must stop it before removing.

docker rm -f my-nginx
✓

Confirm it is really gone

No more my-nginx row. The image is still on your disk though — only the container was deleted.

docker ps -a
8

Go inside a container

⏱ 5 min

A container is a real little Linux machine. Let's walk around in it.

✓

Open a shell inside a Python container

-it = interactive terminal (you can type in it) · --rm = delete the container automatically when you leave · bash = the program to run instead of the default one.

docker run -it --rm python:3.11-slim bash
What you should see
root@e3b0c4429813:/#   <- your prompt changed! you are inside now

Your prompt changed — you are now typing inside the container. Try these (they run in the container, not on your laptop):

✓

Which Python is in here?inside container

The image ships with Python 3.11 regardless of what is installed on your laptop.

python --version
✓

What operating system is this?inside container

Debian Linux — even if your laptop is Windows. The container brings its own OS user-space.

cat /etc/os-release
✓

Look around the filesysteminside container

A complete Linux file tree that has nothing to do with your laptop's files.

ls /
✓

Prove it is isolatedinside container

Create a file. It exists only inside this container, and disappears forever when you exit (because of --rm).

touch /i-was-here.txt && ls /
✓

Leave the containerinside container

Ends the shell, which ends the container's main process, which stops the container. Container lifetime = the lifetime of its main process.

exit
💡 Why that matters

A container is not a virtual machine that boots and idles. It runs one process. When that process ends, the container stops. That is why a container running bash dies the moment you type exit.

9

Volumes: let a container see your files

⏱ 6 min

Containers are sealed. A volume punches a hole so the container can read a folder on your laptop.

There is a file called whoami.py in your project folder. We are going to run it with a Python container — without installing Python and without building anything.

✓

Run your local script inside a container

-v <folder on your laptop>:<folder in the container> mounts your current folder into the container at /app. Then we tell the container to run the file it now finds there.

docker run --rm -v "${PWD}:/app" python:3.11-slim python /app/whoami.py
docker run --rm -v "$(pwd):/app" python:3.11-slim python /app/whoami.py
What you should see
  Hello! I am a Python script running in Docker
  Python version : 3.11.x
  Machine name   : 7f3a2b1c9d8e   <- container ID
💡 What ${PWD} / $(pwd) means

It is your terminal saying “the folder I am currently in”. That is why Step 2 (cd project) mattered. If you are in the wrong folder, the container mounts the wrong folder and Python reports can't open file '/app/whoami.py'.

✅ Real-world use

This is how you test code against another Python version in 5 seconds, and how databases keep their data alive when the container is deleted. Volumes = the container's link to the outside world.

10

Build your own image

⏱ 18 min

The main event. We turn our FastAPI app into an image anyone in the world can run.

A Dockerfile is a recipe. docker build follows the recipe and bakes an image. Open project/Dockerfile in your editor — here it is:

📄 project/Dockerfile
# ---------------------------------------------------------------
#  Week 18 - Day 1 : our first Dockerfile
#  A Dockerfile is a RECIPE. `docker build` bakes it into an IMAGE.
#  Every line below becomes one LAYER of that image.
# ---------------------------------------------------------------

# 1. Start from an official image that already has Python inside.
FROM python:3.11-slim

# 2. Every command after this runs inside /app in the container.
WORKDIR /app

# 3. Copy ONLY requirements first. Why? Layer caching:
#    if your code changes but requirements don't, Docker reuses
#    the cached pip layer and the rebuild takes ~1 second.
COPY requirements.txt .

# 4. Install the dependencies inside the image.
#    --no-cache-dir keeps the image small.
RUN pip install --no-cache-dir -r requirements.txt

# 5. Now copy the application code (this is what changes most often).
COPY app.py .

# 6. Documentation: this app listens on port 8000.
EXPOSE 8000

# 7. The command that runs when the container starts.
#    --host 0.0.0.0 is REQUIRED: 127.0.0.1 inside a container
#    would only be reachable from inside the container itself.
CMD ["uvicorn", "app:app", "--host", "0.0.0.0", "--port", "8000"]
💡 The one line beginners always get wrong

--host 0.0.0.0 in the last line. Inside a container, 127.0.0.1 means “only this container”, so your browser would never reach it. 0.0.0.0 means “accept connections from outside too”. Forget it and you get an empty browser page with a perfectly healthy-looking container.

✓

Build the image

-t docker-demo:v1 names and tags it · the . at the end means “the recipe and the files are in this folder”. Watch the numbered steps scroll past — each one is a layer.

docker build -t docker-demo:v1 .
What you should see
=> [1/5] FROM python:3.11-slim
=> [2/5] WORKDIR /app
=> [3/5] COPY requirements.txt .
=> [4/5] RUN pip install --no-cache-dir -r requirements.txt
=> [5/5] COPY app.py .
=> naming to docker.io/library/docker-demo:v1
✓

Find your image in the list

It is yours, it is local, and it is a first-class image exactly like the ones you downloaded.

docker images docker-demo
✓

Run your image

Same flags as nginx: background, port 8000 mapped to 8000, with a name.

docker run -d -p 8000:8000 --name demo-api docker-demo:v1
✅ Open your app 🎉

http://localhost:8000 — then try /health and /predict?value=21.

Also try /docs — FastAPI's automatic API documentation, running inside your container.

✓

Test it from the terminal too

The same check a monitoring system or a deployment pipeline would run.

curl.exe http://localhost:8000/health
curl http://localhost:8000/health
What you should see
{"status":"healthy"}

ⓘ On Windows it must be curl.exe — plain curl in PowerShell is a different, older command.

✓

Read your app's logs

Every request you made from the browser is in there. First stop for any bug.

docker logs demo-api
✓

Step inside your own running container

Opens a shell in the container that is already running. exec = run an extra command in an existing container (run would create a brand new one).

docker exec -it demo-api bash
✓

Look at what you shippedinside container

Your app.py and requirements.txt are in /app exactly as the Dockerfile promised.

ls -l /app
✓

Leave againinside container

Type this to get out. The container keeps running — you only ended the extra shell.

exit

Now change its behaviour without rebuilding

The app reads an environment variable called GREETING. Environment variables are how you configure the same image differently in dev, staging and production.

✓

Remove the old container

A name can only be used once, so free it up first.

docker rm -f demo-api
✓

Run it again with your own message

-e NAME=value passes an environment variable in. Put your own name in the quotes, then refresh http://localhost:8000.

docker run -d -p 8000:8000 -e GREETING="Hello from YOUR NAME" --name demo-api docker-demo:v1
11

Layer caching — why the second build is instant

⏱ 6 min

This is the trick that makes Docker usable day to day.

Open project/app.py in your editor. Find the line that says <h1 style="margin:8px 0">It works!</h1> and change the text to something of your own. Save the file.

✓

Build again, as version 2

Watch the output closely: the pip install step says CACHED. Docker knows requirements.txt did not change, so it reuses that layer and only redoes the COPY app.py step. Seconds instead of minutes.

docker build -t docker-demo:v2 .
What you should see
=> CACHED [4/5] RUN pip install --no-cache-dir -r requirements.txt
=> [5/5] COPY app.py .
=> naming to docker.io/library/docker-demo:v2
💡 That is why the Dockerfile copies requirements first

If we had copied all the code before installing the packages, every one-character code change would throw away the cache and reinstall every dependency from scratch. Cheap rule, huge payoff: put the things that rarely change at the top of your Dockerfile.

✓

Remove the old container

The name demo-api is still taken by the v1 container.

docker rm -f demo-api
✓

Start a container from your new image

Same command as before but with the :v2 tag. Refresh http://localhost:8000 to see your edit live.

docker run -d -p 8000:8000 --name demo-api docker-demo:v2
✓

See both versions side by side

Two tags, two images, both yours. Rolling back is just running :v1 again — this is how real deployments undo a bad release.

docker images docker-demo
12

Clean up

⏱ 5 min

Docker never deletes anything on its own. Do this or your disk fills up.

✓

See everything you created today

Running and stopped.

docker ps -a
✓

Remove today's containers

Force-removes both by name. Errors about containers you already deleted are harmless.

docker rm -f demo-api my-nginx
✓

Check how much disk Docker is using

Images, containers, volumes and build cache. The RECLAIMABLE column is what you can get back.

docker system df
✓

Delete all stopped containers

Safe: only removes containers that are not running.

docker container prune -f
✓

Optional — also delete unused images

Frees the most space, but you will have to re-download those images next time. Skip this if your internet is slow — you will want these images for Day 2.

docker image prune -a -f

ⓘ Only run this if you are short on disk space.

The 20 commands that cover 95% of daily Docker use.

IMAGES

  1. Add a new endpoint GET /model-info that returns the model name, version and author (you).
  2. Make /predict multiply by a number read from an environment variable called FACTOR instead of always doubling (hint: os.getenv("FACTOR", "2")).

💡 How to debug it when it breaks
  1. docker ps -a — did the container even stay up?
  2. docker logs <name> — the Python error will be right there
  3. Fix app.py, then rebuild — editing the file does not change the image

That third point catches everyone: an image is a frozen snapshot. Change code → rebuild → rerun.

Troubleshooting — every error you might hit

⏱ —

Find your error message here before asking.

You see thisDo this
Cannot connect to the Docker daemon
error during connect ... docker_engine		Docker Desktop is not running (Windows/Mac): open it from the Start menu and wait until the whale icon stops animating. On Linux: sudo systemctl start docker
permission denied while trying to connect to the Docker daemon socket (Linux)sudo usermod -aG docker $USER then log out and back in. As a one-off you can put sudo in front of the docker command.
Bind for 0.0.0.0:8000 failed: port is already allocatedSomething else is already using that port — often a container you forgot. Run docker ps, then docker rm -f <name>. Or just use a different port on your side: -p 8001:8000 and browse to :8001.
The container name "/demo-api" is already in useYou already have a container with that name. docker rm -f demo-api then run again.
The browser shows "can't be reached" but docker ps says it's runningThree usual causes: (1) the -p numbers are the wrong way round, (2) the app inside is bound to 127.0.0.1 instead of 0.0.0.0, (3) you are using the wrong port in the URL. Check docker logs <name>.
py or python is not recognised (Windows)Try the other one. If Windows opens the Microsoft Store instead, install Python from python.org and tick “Add python.exe to PATH” during install.
Activate.ps1 cannot be loaded because running scripts is disabled (Windows)Run Set-ExecutionPolicy -Scope Process -ExecutionPolicy Bypass -Force first, then activate again. It only affects that one window.
ensurepip is not available (Ubuntu)sudo apt install -y python3-venv then create the virtual environment again.
docker run -it hangs or shows garbage (Windows)You are in Git Bash. Use PowerShell instead. (If you must use Git Bash, prefix with winpty.)
can't open file '/app/whoami.py'Your terminal is not in the project folder, so ${PWD} pointed somewhere else. cd into project and try again.
The pull is crawling / the wifi is dyingAsk the instructor for the offline image file, or use labs.play-with-docker.com to follow along in the browser.
Ctrl+C doesn't stop my containerIf you started it with -d it is in the background — Ctrl+C only stops the log view. Use docker stop <name>.
I edited app.py but nothing changedAn image is a snapshot taken at build time. You must docker build again, then remove and rerun the container.
